# Audit — what this tool claims to be, and what it is

**Date:** 2026-08-16
**Method:** read the specification and status docs, then used the tool as a user would:
built a real CMake/C++ project with deliberate build pathologies
(`examples/cmake-cpp/`), wrapped it in BuildStream elements, and tried to run a
complete macro→micro optimization cycle against it. Every claim below was
executed, not inferred. Commands are reproducible from the repo.

This complements [`conformance_review.md`](conformance_review.md), which audits
the implementation against `specification.md` line by line. **This document
audits the specification itself against the job the tool is supposed to do.**
The two findings are different in kind and both matter:

> `conformance_review.md`: *the implementation does not do what the spec says.*
> This document: *what the spec says is not enough to optimize a build.*

The resulting work is tracked in [`scenarios.md`](scenarios.md); the target
architecture is in [`design_directions.md`](design_directions.md).

---

## 1. What it claims to be

| Source | Claim |
| --- | --- |
| `README.md` | *(one line: the repo name — no claim at all)* |
| `specification.md` §1 | "extract, analyse, and **visualise** BuildStream dependency graphs with high performance and reusability" — a Python extractor plus a static HTML G6 viewer |
| `specification.md` §8 | interactive at 100k nodes / 300k edges |
| `IMPLEMENTATION_STATUS.md` | Phases 0–5 "✅ COMPLETE", only integration tests pending |
| Repo/branch naming, and the framing of this task | a **build optimization** tool |

Those are three different products, and only the second one is written down
anywhere. That gap is the root finding of this audit.

## 2. What it actually is, today

A Python package that shells out to `bst show`, parses a text format that
BuildStream does not emit, builds a `networkx` DiGraph, computes several graph
metrics — and then discards nearly all of them before writing the file. Plus a
directory of JavaScript modules that cannot be loaded by any JS engine and for
which no HTML page, bundler, or dependency manifest exists.

Verified independently during this audit:

```
$ node --input-type=module -e "import('./viewer/main.js')"
FAILED: SyntaxError Unexpected identifier 'assert'
$ ls *.html viewer/*.html package.json
(no matches — Tool 2 as specified does not exist in any form)
$ find . -name '*test*' -not -path './.git/*'
(no matches — zero tests)
$ python3 -c "import networkx"
ModuleNotFoundError  (no requirements.txt / pyproject.toml anywhere)
```

`conformance_review.md` documents ~40 further defects at this level. They are
real and this audit reproduced the headline ones. **They are not repeated
here** — the rest of this document is about the layer above them.

## 3. The walkthrough — trying to optimize a real project

Setup: `examples/cmake-cpp/` — 15 BuildStream elements wrapping a 5-target
CMake/C++ build with three deliberately planted pathologies (a false
`cmake→openssl` build-depend, a false `mathlib→netlib` depend mirrored in the
C++ `#include`s, and a kitchen-sink `base/sdk.bst`). See that directory's
README for the full description and reproduction commands.

### 3.1 Step 1 — point the tool at the project. It silently reports success on garbage.

```
$ bst show --deps all --format '%{name}|%{kind}' app/stack.bst   # 15 elements
$ python3 -m bst_graph_extractor.cli app/stack.bst -o graph.json -v
INFO [cli] Parsed 15 nodes and 0 edges
INFO [graph_builder] Built graph with 1 nodes and 0 edges
INFO [serializer] Output validation passed
INFO [cli] Extraction completed successfully in 49.00ms
$ echo $?
0
```

A 15-element project became a **1-node, 0-edge** graph, and the tool exited
`0` claiming success and schema validity. The single node it emitted:

```json
{"id": "buildable",
 "data": {"label": "app/stack.bst",
          "kind": "0000000000000000000000000000000000000000000000007e3f79..."}}
```

The extractor calls a bare `bst show TARGET`, gets BuildStream's real default
format (`%{state} %{full-key} %{name}`), splits on whitespace, and takes the
*state word* as the node id — so all 15 lines collapse onto one node called
`buildable`, with the cache key as its `kind`.

This is the worst possible failure shape. The spec's own principle 9 is *"Fail
Closed, Diagnose Fast — on invalid input both tools stop and explain precisely
what went wrong, never proceed on partially-trusted data."* Here the tool
proceeds on entirely-wrong data, and its own schema validation passes, because
nothing in the schema says "a 15-line input should not produce 1 node."

The mechanism is `parser.py:96-100`: `except Exception: continue` — malformed
lines are dropped silently unless `--show-invalid` is passed. A parse that
drops 100% of its input is indistinguishable from a parse that drops none.

### 3.2 Step 2 — feed it the format its own spec documents. Still zero edges.

Both of the spec's §3.2 invocations were rendered by the shim and fed directly
to `parse_bst_show_output`:

| Input | Result |
| --- | --- |
| `--format '%{name}\|%{kind}'` | 15 nodes, **0 edges** |
| `--format '%{name}\|%{deps}'` | 15 nodes, **0 edges** — `kind` parsed as the literal string `[]` |

The `%{deps}` list form `[a, b, c]` — the only invocation that carries edges at
all — has no parsing code path. **There is no invocation of the real `bst` CLI,
documented or otherwise, from which this tool can obtain a dependency graph.**
The only format that yields edges is an invented `id|kind` + `- dep`
continuation grammar that `bst show` never produces.

### 3.3 Step 3 — work around the parser. Now every metric is empty.

With a compatibility mode in the shim emitting the invented grammar, the graph
finally builds — and the analysis is uniformly blank:

```
$ python3 -m bst_graph_extractor.cli app/stack.bst --include-runtime \
      --expensive-metrics --performance-report -o macro.json
nodes 15  edges 32  cp 10  maxTopoLayer 10  width 3
levelCounts {'0': 15}          # every element claims to be in layer 0
combos 0                       # no hierarchy, ever
node base/toolchain.bst: inDegree 0, outDegree 0, topoLayer 0, cpDepth 0,
    isCritical False, isArticulationPoint False,
    blastRadius null, buildCost null, bottleneckScore null
```

The graph-level numbers are right (32 edges, critical path 10). Every
*per-node* value is a default — the metrics are computed and then dropped at
serialization (`conformance_review.md` §2.1). So the one question a user
actually asks — *which element should I fix?* — has no answer in the output.

`base/toolchain.bst` is the single articulation point of this graph and reports
`isArticulationPoint: false`. Independent `networkx` computation on the same
extracted graph finds it correctly.

### 3.4 Step 4 — edge direction is inverted relative to the spec

`parser.py:159` emits `source=dependency, target=dependent`. The spec's own
§3.4.1 example payload has `source: components/desktop/gtk.bst`, `target:
base/linux-headers.bst` — dependent → dependency, the opposite.

This is not cosmetic. §3.3 defines `blastRadius` as *downstream reachable* and
`buildCost` as *upstream reachable*. Under inverted edges the two swap
meaning, so a consumer that trusts the schema gets "how many things must build
before me" when it asks "how many things break if I touch this." Nothing
catches it because both fields are `null` today anyway.

### 3.5 Step 5 — there is no viewer, so the cycle ends here

Spec §1 defines Tool 2 as a self-contained `bst_graph_viewer.html`. No HTML
file exists; the ES modules do not parse; `@antv/g6` is absent in every form.
The extraction output has no consumer.

## 4. The deeper finding: even a perfect implementation would not optimize a build

Everything above is fixable with the R0–R25 tasks already in
`conformance_review.md`. Suppose all of it is fixed tomorrow — the extractor
parses real `bst show`, all metrics land in the JSON, the viewer renders 100k
nodes at 60fps. **You still cannot optimize a build with it**, because five
things are absent from the specification, the schema, and the data model.

### 4.1 There is no time anywhere in the model

Search `graph_data.schema.json` for a duration field: there is none. The word
"critical path" in this spec means *the longest chain of edges*. Build
optimization means *reducing wall-clock*, and those are different objectives.

Measured on the example project, with per-element durations attached
(measured for the CMake targets, estimated for base/deps layers):

```
total work   501.6 s      makespan (unbounded workers)   400.5 s
                          ideal speedup                    1.25x
```

The build is 80% serial. Now compare two single-edge fixes — both remove
exactly one edge, both shorten the *edge-count* critical path by exactly 1:

| Change | CP (edges) | makespan | saving |
| --- | --- | --- | --- |
| baseline | 10 | 400.5 s | — |
| cut `mathlib → netlib` | 9 | 399.4 s | **1.1 s** |
| cut `cmake → openssl` | 9 | 340.5 s | **60.0 s** |

**The tool ranks these two fixes identically.** One is worth 0.3% and the other
15%, and no metric in the schema can tell them apart. A user following the
tool's advice has a 50% chance of spending their afternoon on the wrong edge.
This is the single most important finding in this document.

### 4.2 There is no cache model — and for BuildStream that is most of the answer

BuildStream's defining feature is content-addressed caching: an element whose
cache key is unchanged is *fetched*, not built. In CI, most of the dependency
graph is a cache hit on most runs.

An element's real expected cost is `P(cache miss) × build duration`, not
`build duration`. `base/toolchain.bst` is the most expensive element in the
example (180 s) and the graph's only articulation point — and it is also the
element that changes twice a year, so its expected contribution to a typical CI
run is near zero. Optimizing it is worthless; the tool would rank it first on
every axis it has.

Conversely the cheap `src/*` elements rebuild on every commit, so their
*structure* — how much they force each other to rebuild — is where the money
is. Nothing in the model distinguishes these cases.

### 4.3 There is no scheduler — critical path is not makespan

Real builds run at a finite job count. `makespan(j)` needs a list-schedule
simulation over `(graph, durations, j)`; only at `j → ∞` does it degenerate to
the time-weighted critical path, and never to the edge-counted one. Without it
the tool cannot answer "would more CI workers help, or am I latency-bound?" —
which is the first question anyone asks. (On this example: `makespan(4) ==
makespan(∞) == 400.5 s` — adding workers does nothing, the build is
latency-bound. That is an actionable finding the tool structurally cannot
produce.)

The related per-node quantity is **slack** — how long an element can be delayed
before it extends the build. Slack, not degree or betweenness, is the correct
prioritizer for optimization work, and it does not exist in the model.

### 4.4 There is no micro level — nothing is read from the native build system

The task framing asks the tool to "dig info from the native build system."
Today it reads exactly one input, `bst show`, and knows nothing about what
happens inside an element. Everything below is present in the example build,
free to collect, and entirely unused:

| Available artifact | What it yields | Currently used |
| --- | --- | --- |
| `.ninja_log` | per-target start/end ms → real durations, real parallelism trace | ✗ |
| `compile_commands.json` | per-TU flags, include paths | ✗ |
| `ninja -t deps` | full header→TU dependency graph | ✗ |
| `ninja -t graph` | native build DAG | ✗ |
| `-ftime-trace` / `-ftime-report` | intra-TU cost breakdown | ✗ |
| `bst build` logs / cache keys | element durations, cache hit/miss | ✗ |

Doing the micro pass by hand on the example, with data the tool ignores:

```
$ ninja -t deps | ... reverse-index project headers by including TU
     12  libs/corelib/include/corelib/core_all.hpp     <- 12 of 13 TUs
      3  libs/mathlib/include/mathlib/linalg.hpp
```

```
compile hash.cpp with core_all.hpp   : 519 / 554 / 550 ms   (84,622 preproc. lines)
compile the same TU with id.hpp only : 149 / 163 / 149 ms   (25,269 preproc. lines)
```

≈ 400 ms × 12 TUs ≈ **4.8 s of the 16.7 s of CPU work in this build is one
header being included by translation units that need one `typedef` from it.**
And the incremental cost:

```
touch corelib/core_all.hpp  -> 17 ninja steps, 1796 ms
touch utillib/src/timeutil.cpp -> 3 ninja steps,  616 ms
```

None of this is visible at the element level. `src/corelib.bst` looks like a
2-second element — a rounding error next to the 180-second toolchain — while
being the cause of most of the *repeated daily* cost. **The macro and micro
levels disagree about what matters, and the tool only has one of them.**

### 4.5 There is no history, baseline, or regression concept

Every run is a standalone snapshot. There is no baseline artifact, no
comparison, no notion of "this got worse." The CI use case in the task
framing — *stop regressions that leave big room for optimization* — has no
foundation at all in the current data model: nothing to compare against,
nothing normalized to compare *with*, and no cost data to compare in the first
place.

## 5. Positioning: pick one

The repo is currently two products fighting for the same budget.

**(a) A large-graph visualizer.** The spec is genuinely strong here — the
dataset/render mode split, LOD tiering, budget clamping, the honesty
principles. It is also where ~70% of the spec's complexity sits: §2, §4.3–4.11,
§5 are almost entirely about rendering 100k nodes without dropping frames.

**(b) A build efficiency tool.** Needs cost, cache, scheduling, native-build
ingestion, baselines, and a ranked worklist. Topology is maybe 20% of it, and
**the rendering scale that dominates the current spec is largely irrelevant to
it** — the answer to "what should I fix?" is a ranked list of 20 items and a
handful of subgraphs, not a 100k-node canvas.

Recommendation: **(b), with the viewer demoted to one surface among several.**
Grounds: the CI scenario cannot consume a canvas at all, it needs numbers and a
verdict; the local scenario needs the ranked worklist first and the picture
second; and the picture is only worth drawing once the nodes carry cost and
slack, which is exactly what (b) adds. Keep the viewer's honesty and
progressive-disclosure principles — they are the best part of the existing
spec — and drop the 100k-node performance envelope until something actually
needs it.

If (a) is chosen instead, that is a legitimate call — but then the optimization
framing should be removed from the project's goals, because none of §4 above
is on the roadmap.
